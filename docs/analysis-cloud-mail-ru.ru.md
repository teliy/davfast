# Почему веб-интерфейс cloud.mail.ru загружает быстро — и как davfast это повторяет

Разбор механизмов веб-интерфейса и WebDAV-шлюза, причины медленности davfs2 и как каждый пункт решён в davfast.

## 1. Что происходит, когда файл грузится через веб-интерфейс

Веб-приложение cloud.mail.ru **не использует WebDAV** для передачи данных. Открытые реализации (kireevmp/mailru-cloud-api, mad-gooze/PyMailCloud, бэкенд rclone `mailru`) описывают такой поток:

| Шаг | Запрос | Назначение |
|---|---|---|
| 1 | `POST https://auth.mail.ru/cgi-bin/auth` (Login, Password, Domain) | веб-сессия, cookies |
| 2 | `POST https://cloud.mail.ru/api/v2/tokens/csrf` | CSRF-токен (`body.token`, живёт ~сутки; при 403 — перелогин) |
| 3 | `GET https://cloud.mail.ru/api/v2/dispatcher?api=2&x-email=...&token=...` | список узлов: `body.upload[...]` и `body.get[...]` (URL вида `https://cld-uploaderXXX.cloud.mail.ru/upload-web`) |
| 4 | `PUT {upload-узел}?x-email=...&cloud_domain=2`, тело файла | содержимое уходит напрямую в upload-кластер; ответ `"<hash>;<size>"` |
| 5 | `POST https://cloud.mail.ru/api/v2/file/add` (home, hash, size, token) | регистрация файла в облаке |
| 6 | `GET {download-узел}{/полный/путь}` | скачивание (с cookies сессии) |

Список каталогов: `GET /api/v2/folder?home=...&token=...` → `body.list[]` с полями `type` (`file`/`folder`), `home`, `name`, `size`, `mtime`, `hash`. Информация об объекте: `GET /api/v2/file?home=...`. Создание каталога: `POST /api/v2/folder/add` (home). Удаление: `POST /api/v2/file/remove` (home, рекурсивно для каталога). Перемещение: `POST /api/v2/file/move` (home, folder).

Ключевые ответы API приходят в JSON-конверте `{"status":200,"email":...,"body":...,"time":...}`; ошибка — `status != 200`, тело ошибки в `body`.

### Дедупликация по хешу

Хеш файла — «модифицированный SHA-1» (совместим с rclone):

- файл > 20 байт: `sha1(содержимое || десятичная_длина)`;
- файл ≤ 20 байт: `sha1(содержимое, дополненное нулями до 20 байт)`.

Если облако уже хранит содержимое с таким хешем, шаг 4 можно пропустить вообще: `file/add` с готовым хешем завершается мгновенно (в rclone это называется speedup / put-by-hash). Именно поэтому повторная загрузка в веб-интерфейсе почти мгновенна.

## 2. Откуда у веб-интерфейса скорость

1. **Нет лишних round-trip'ов на файл.** Веб-клиент не делает PROPFIND/stat перед каждым файлом: он кладёт файл и обновляет состояние из ответа API.
2. **Параллельная очередь загрузок.** Очередь мелких файлов уходит пачкой в несколько одновременных HTTP-запросов; браузер мультиплексирует их (HTTP/2 / keep-alive) в одно соединение.
3. **Прямой upload-кластер.** Данные идут на выделенные узлы `cld-uploaderXXX`, а не через общий шлюз.
4. **Дедупликация по хешу.** Уже известное облаку содержимое не передаётся вовсе.
5. **JSON вместо XML.** Ответы компактнее и разбираются быстрее, чем multistatus-XML WebDAV.
6. **Один аккаунт-контекст.** Cookies + CSRF-токен вместо Basic-аутентификации на каждый запрос (экономия заголовков минимальна, но шлюзу WebDAV традиционно ставят пониженные лимиты).

## 3. Почему davfs2 медленный

Известная проблема (обсуждения на linux.org.ru, рекомендации самой Mail.ru):

1. **3 запроса на файл**: PROPFIND (stat) → PUT → PROPFIND (обновить кэш атрибутов). При RTT 50 мс это ~150 мс накладных на файл, т.е. потолок ~7 файлов/с.
2. **Операции по сути последовательные**: VFS дергает FUSE синхронно, кэш атрибутов davfs2 часто промахивается.
3. **Соединения и LOCK**: без тонкой настройки davfs2 плодит соединения; LOCK-запросы на облаке бесполезны (Mail.ru сама советует `use_locks 0`).
4. **XML multistatus** на каждый листинг — заметно тяжелее JSON.
5. Каталоги создаются по одному, без параллелизма.

## 4. Что сделано в davfast

| Проблема | Решение в davfast |
|---|---|
| 3 round-trip'а на файл | `list_recursive`: один PROPFIND на каталог (параллельные пакеты) — дерево из тысяч файлов сравнивается за несколько десятков запросов суммарно |
| Последовательность | `futures::buffer_unordered(c)` — все PUT/GET идут с ограниченным параллелизмом (`-c`, по умолчанию 16) |
| Соединения | `reqwest` пул `pool_max_idle_per_host = c`, TCP_NODELAY, TCP keep-alive, HTTP/2 (adaptive window) |
| Каталоги | создание уровнями: родители → дети, внутри уровня параллельно; «уже существует» — не ошибка |
| Повторы | пропуск по размеру (`--skip-existing`) или точно по ETag/хешу из `.davfast-cache.json` (mtime+size+token) |
| Повторная загрузка в mail.ru | режим `mailru`: сначала попытка `file/add` с локальным хешем (дедуп — 0 байт в сеть), затем PUT на upload-узел |
| Ошибки сети | до 3 попыток с экспоненциальной задержкой на 5xx/429/таймауты |
| davfs2-совместимость | мост `serve`: локальный WebDAV → REST облака (или прокси в другой WebDAV), davfs2 монтирует localhost без сетевых потерь, а вся «медленная» работа делается сервером davfast параллельно |

### Замеры (локальная песочница, сеть не участвует)

- 1000 файлов (in-memory DAV-сервер): c=1 — 14 425 файлов/с, c=32 — 17 134 файлов/с (конвейер не сериализуется).
- 320 файлов через отдельный Python DAV-сервер: upload и download — по 0.1 с, побайтовая идентичность.
- Повторный `sync` неизменённого дерева (320 файлов): 0.013 с.

В реальной сети узкое место — RTT: `c` параллельных потоков дают примерно `c / RTT` файлов/с. При 50 мс: c=16 → ~320 файлов/с, c=64 → ~1000+ файлов/с против ~7 файлов/с у davfs2 с его 3-запросным циклом на файл.

## 5. Ограничения и практические советы

- mail.ru требует **пароль для внешних приложений** (id.mail.ru → Безопасность → «Пароли для внешних приложений», доступ «К почте, облаку, календарю»), основной пароль для API не подходит. Максимум файла — 2 ГБ на бесплатных тарифах.
- mailru-бэкенд реализован по открытым источникам; живая проверка с реальным аккаунтом может вскрыть нюансы форматов (все эндпоинты переопределяются переменными окружения `DAVFAST_MAILRU_*`).
- Dispatcher-ответы бывают двух форм (`[{"url":...}]` и `{"count":n,"url":[...]}`) — davfast принимает обе.
- Для davfs2-моста оставьте `use_locks 0` в `/etc/davfs2/davfs2.conf`.
